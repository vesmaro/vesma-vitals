# D-0003: Границы метрик-семейств — тема или вопрос владельца, никогда ярус

Дата: 2026-09-09 · Статус: принято (ArchCom, синтез председателя подтверждён обоими
возражавшими; mnemos `061398fe`)

## Решение

Правило границы семейства: **семейство = тема или один фальсифицируемый вопрос
владельца, никогда ярус** («value»/«health» — не темы). Новое семейство рождается
⇔ (i) нет существующей семьи-владельца для величины И (ii) директива владельца
ставит один вопрос со своим компаратором. Прецедент рождения — F8 «Memory value»:
нетто-ценность in-the-loop не помещается ни в F2, ни в F3, ни в F5 по отдельности.

Применение:

- Заводится **ровно одно** новое семейство — **F9 «Subsystem health»** — и оно
  health-only навсегда (не принимает value).
- F10 «Value подсистем» **не заводится**: все его кандидаты имеют семьи-владельцев
  — CCR-redemption и context_rewrite-redemption → F3; auto-collect adoption и
  checkpoint-return → F5; refine-качество → F2 (McNemar уже спроектирован в
  ADR-0020 mnemos); auth-bypass-probe → F6 (пробу исполняет S4-механика); будущий
  federation-value → F8.
- Инварианты селятся там, где стенд, который их гоняет (прецедент:
  cross-principal-leak = 0 живёт в F7).

## Почему

- F10 по ярусу разрезал бы обещание CCR «сжал — выкупил» между F3 (reduction) и
  F10 (redemption), разрушая продольную читаемость одного обещания.
- Два семейства по подсистемам (Federation / Mechanical) — один и тот же вопрос
  владельца «работает ли подсистема» в двух семьях: таксономия должна следовать
  вопросам, а не категориям реализации.
- Value-читаемость для владельца даёт claims-ledger (обещание → семья → метрика →
  статус), а не семья-папка.

## Условия принятия

- Суб-светофоры F9: строка на подсистему (иначе красный не actionable).
- F9 не аккумулирует value — любая величина «доказанная польза» уходит в семью-владельца.
- Сверка имён метрик с экспериментом ADR-0025 mnemos (E0) — тем же PR, что заводит
  F8/F9-ростер: одна величина — одно имя.
